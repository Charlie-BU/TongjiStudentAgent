# Doc Generator（文档生成与优化）

用于处理与本工程相关的中文 Markdown 文档请求，覆盖三类场景：

- 从零生成完整文档
- 在已有文档中补写或重写局部片段
- 在不改变原意的前提下优化既有文档的结构与可读性

它既负责把碎片信息整理成文，也负责把已有文档打磨到可直接交付的状态；不再依赖其他文档类 Skill 串联调用。

## 事实来源优先级（强制）

1. 当前工程项目源代码（第一可信来源）
2. 用户提供的片段与补充说明
3. 现有 `docs/` 文档（用于风格与历史背景参考，不可覆盖源码事实）

若用户片段、原文内容与源码现状不一致，必须先定位并解释差异，再按用户意图写“现状 / 计划 / 已完成”的准确表述，禁止把未落地内容写成已实现事实。

## 触发时机

- 用户给出零散片段、草稿要点、聊天记录式输入，希望整理成正式文档
- 用户明确要求“按我的文档风格写”
- 用户要求对已有 Markdown 做润色、优化、重写，但强调不改变原意
- 用户要求只补写/改写某一段、某个章节、某个占位符（局部片段生成）
- 需要同时兼顾事实校验、风格贴合和 Markdown 可读性优化

## 输入

- 用户提供的碎片化内容，或已有 Markdown 文档 / 文件路径
- 目标文档主题（若未给出，需先归纳一个准确主题）
- 目标文件名（若需新建且未指定，基于主题生成 kebab/upper-snake 风格文件名）
- 风格参考范围：`references/` 下已有中文文档（如 `ARTICLE1.md`、`ARTICLE2.md`）
- 与片段相关的源码上下文（文件、模块、函数、配置、调用链）
- 若是局部片段生成或既有文档优化，必须额外读取并理解目标文档上下文（前后段、章节语气、叙述节奏）
- 用户额外约束（如“不要改语气”“不要删信息”“只改结构不改观点”）

## 表达约束

- 能一句话说清的内容，不要展开成一段。
- 不要为了“完整”重复同一个意思，不写车轱辘话。
- 不刻意套“背景 / 目标 / 方案 / 收益”等这类固定模板；结构服从内容本身。
- 强调“不要 AI 味”，删掉空话、套话和过度过渡句。
- 优化现有文档时，默认遵守“信息守恒优先于排版整齐”。

## 执行步骤

1. 先识别任务模式。
    - 在“整篇生成 / 局部补写 / 原文优化”三种模式中做明确判断。
    - 若用户同时要求“补内容 + 调结构”，按“先补齐事实、再统一优化”的顺序处理。

2. 收集输入并建立信息清单。
    - 把输入拆成“事实、判断、过程、结论、待确认点”。
    - 对冲突信息先标记，不擅自拍板。
    - 优化既有文档时，先列出必须保留的信息点、术语、边界条件。

3. 做源码对齐与事实校验。
    - 以当前工程源码为第一可信来源，定位片段对应的模块、文件、函数、配置和调用关系。
    - 区分“已在代码中实现”“仅在讨论中提出”“计划中但未落地”三种状态。
    - 无源码或用户明确证据支撑的内容，不写为既成事实。

4. 建立最小必要工程上下文。
    - 根据片段、原文和源码中出现的模块、术语、变量、流程补齐背景。
    - 目标读者默认为 0 上下文读者，确保文档可独立阅读。
    - 仅补齐理解当前主题所必需的背景，不扩写无关内容。

5. 建立风格优先级。
    - 若是局部补写或原文优化：先对齐目标文档整体风格，再对齐作者个人文档风格。
    - 若是整篇生成：优先对齐作者个人文档风格，并保持全文风格一致。
    - 参考 `references/` 下既有文风：第一人称、复盘视角、技术细节具体。

6. 组织内容并完成改写。
    - 生成场景：先提炼主问题与核心结论，再将碎片挂接到同一条逻辑链。
    - 优化场景：在保证语义等价的前提下，重排段落、拆分长句、补齐必要标题层级与 Markdown 结构。
    - 所有场景都要优先写清设计动机、设计取舍和问题闭环，避免只罗列实现步骤。
    - 保留用户原有语气强度，不改写成模板化公文。

7. 做可读性与排版增强。
    - 合理使用标题、列表、引用和行内代码提升扫描效率。
    - 统一中文、英文、数字混排时的可读性。
    - 长段落拆成短段和列表，但不为了整齐牺牲原文信息密度。

8. 不确定信息先提问确认（强制）。
    - 当“设计动机 / 取舍依据 / 问题定义”缺失，或存在多种合理解释时，不得自行脑补。
    - 必须先向用户抛出澄清问题，拿到确认后再写入文档。

9. 输出前做一致性回检。
    - 检查“处理前意图”与“处理后表达”是否一致。
    - 检查关键信息是否遗漏、状态是否前后矛盾、术语是否误替换。
    - 若是优化场景，确认原文立场、结论、边界没有被改写。

## 输出 / 质量门槛

- 输出物：可直接交付的 Markdown 内容；若目标是现有文件，则就地更新
- 必须满足：
    - 源码一致：关于实现现状的描述可在当前工程源码中找到对应依据
    - 意图准确：能清晰表达用户真正想表达的含义
    - 信息完整：碎片中的关键事实与结论不丢失
    - 信息守恒：若为优化或局部改写，原文要点、立场、边界 100% 保留
    - 片段一致：若为局部片段，能无缝融入原文，不破坏整篇文章叙事与语气
    - 风格贴合：读起来与目标文档和 `references/` 既有文档风格一致
    - 可读性强：0 上下文读者可读懂问题、过程与结论
    - 深度到位：明确回答“为何设计、为何这样设计、解决了什么问题”
    - 结构自然：逻辑顺序来自内容本身，不强套固定模板

## Language Style Rules

### 目的

- 降低 AI 生成文本的模板痕迹，提升表达自然度与可读性。

### 句式约束

- 避免盲目、过度使用“不是...而是...”句式。
- 同一段内最多使用一次该句式；若无必要，优先不用。
- 当该句式不承载明确对比关系时，必须改写为更直接表达。

### 推荐替代方式

- 直接陈述结论，再补充原因或边界。
- 使用“重点是”“核心在于”“更准确地说”“换句话说”等过渡表达。
- 通过并列短句表达差异，避免固定二元对照模板。

### 反例与正例

- 反例：这不是流程文档，而是能力闭环文档；这不是单点优化，而是系统升级。
- 正例：这是一份能力闭环文档。它覆盖流程说明，也强调可执行约束。

## 禁止事项

- 禁止在信息不足时臆造关键事实
- 禁止脱离当前工程源码上下文直接“脑补实现细节”
- 禁止为了“看起来规范”而篡改用户原始立场
- 禁止忽略冲突片段并直接合并为单一结论
- 禁止在优化既有文档时新增未经原文或源码支持的结论
- 禁止仅罗列实现步骤而不解释设计动机与问题闭环
- 禁止在关键动机不确定时跳过澄清，直接下结论写入文档
- 禁止为了凑结构刻意套模板，写出明显的 AI 腔
- 禁止同义反复、空洞总结、机械收束

## 后续纠偏原则

- 用户后续若对文档事实或结论纠偏，以最新说明为准。
- 纠偏采用最小改动原则，仅修改受影响段落并保持整体风格一致。
- 若纠偏影响上下文一致性，需同步更新标题、状态描述与结论段。
